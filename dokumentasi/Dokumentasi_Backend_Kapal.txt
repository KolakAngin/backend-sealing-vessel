DOKUMENTASI BACKEND APLIKASI SEGEL KAPAL
Tahap 6 - Pengujian dan Dokumentasi API
Tanggal verifikasi: 7 September 2026

1. RINGKASAN


Backend Aplikasi Segel Kapal dibuat dengan Node.js, TypeScript, Express,
Prisma ORM, dan PostgreSQL. Sistem menyediakan autentikasi JWT, otorisasi
berdasarkan role, CRUD master data, transaksi laporan sealing, pengelolaan
seal, verifikasi, tanda tangan, audit log, serta lampiran gambar/dokumen.

2. TEKNOLOGI DAN STRUKTUR UTAMA


- Runtime        : Node.js
- Bahasa         : TypeScript (ECMAScript module)
- Web framework  : Express 5
- ORM            : Prisma ORM 7.10.0
- Database       : PostgreSQL
- Validasi input : Zod
- Autentikasi    : JWT menggunakan jose
- Password       : bcryptjs
- Upload         : Multer memory storage + penyimpanan lokal
- Test runner    : Node.js test runner melalui tsx

Direktori penting:

- prisma/schema.prisma       Skema database
- prisma/migrations/         Riwayat migrasi
- prisma/seed.ts             Seed admin dan master data
- src/routes/                Definisi endpoint
- src/controllers/           HTTP controller
- src/services/              Aturan bisnis dan query Prisma
- src/schemas/               Validasi request Zod
- src/middleware/            Auth, upload, validasi, error handler
- src/storage/               Penyimpanan lampiran lokal
- tests/                     Integration test
- uploads/                   File lampiran lokal (tidak masuk Git)

4. FORMAT RESPONS

Respons berhasil:

{
  "success": true,
  "message": "Pesan keberhasilan",
  "data": {},
  "timestamp": "2026-09-03T00:00:00.000Z"
}

Respons gagal:

{
  "success": false,
  "message": "Pesan kesalahan",
  "details": [],
  "timestamp": "2026-09-03T00:00:00.000Z"
}

Kode HTTP utama:

- 200 OK
- 201 Created
- 400 request atau aturan bisnis tidak valid
- 401 token tidak tersedia/tidak valid
- 403 role tidak memiliki izin
- 404 data tidak ditemukan
- 409 konflik data/relasi
- 413 file melebihi batas ukuran
- 415 format file tidak didukung
- 500 kesalahan internal server

6.8 Shipment/Voyage dan laporan sealing

Endpoint canonical:

- GET    /shipments atau /voyages
- POST   /shipments atau /voyages
- GET    /shipments/:id atau /voyages/:id
- PATCH  /shipments/:id atau /voyages/:id
- DELETE /shipments/:id atau /voyages/:id
- POST   /shipments/:id/prepare-seals atau /voyages/:id/prepare-seals
- GET    /shipments/:id/validation atau /voyages/:id/validation
- POST   /shipments/:id/finalize atau /voyages/:id/finalize

Create canonical mewajibkan vesselId, activityId, reportDateTime, voyageNumber,
shipmentNumber, productId, loadingPlantId, loadingJettyId, dischargePlantId,
dischargeJettyId, dan sealingStatus. Seluruh master harus aktif; Activity harus
LOADING, DISCHARGE, atau ROB; serta kedua pasangan Plant-Jetty harus mempunyai
assignment. shipmentNumber unik. sealingStatus terpisah dari status perjalanan.
sealingProcessStatus dikelola server dengan nilai NOT_STARTED, IN_PROGRESS,
READY, IN_TRANSIT, VERIFICATION, dan FINALIZED. loadingMasterId merupakan
assignment operasional terpisah dari createdById; unloadingMasterId wajib
ditetapkan sebelum depart.

prepare-seals membaca versi form, VesselFormProfile, section A-H tersedia,
compartment aktif, dan seluruh vessel sealing point aktual. Proses menyimpan
snapshot immutable serta membuat record berstatus NOT_SEALED. Beberapa point
dalam satu compartment didukung. Proses idempotent dan tidak lagi membuat
SYS-COMPARTMENT; record SYS-COMPARTMENT lama tetap dipertahankan. Detail:
dokumentasi/API_FORM_SNAPSHOT.md.

Transaksi pengisian form A-H menggunakan snapshot tersebut:

- GET    /shipments/:reportId/form
- PUT    /shipments/:reportId/form/points/:pointId
- PATCH  /shipments/:reportId/form/points/:pointId
- DELETE /shipments/:reportId/form/points/:pointId
- PUT    /shipments/:reportId/form/sections/:sectionCode

Prefix /voyages dan /reports menyediakan endpoint yang sama. Response GET
mengembalikan section, row, column, compartment, side, instance, sequence,
status, catatan, dan seluruh nomor segel. PUT/PATCH/DELETE/batch hanya diizinkan
ketika DRAFT. Satu compartment dapat mempunyai beberapa point termasuk lima
point Bagian A, dan satu equipment dapat mempunyai beberapa nomor segel.
Section tidak tersedia, termasuk G, tidak dapat diisi. Nomor segel dinormalisasi
uppercase dan mengikuti unique global database. Detail:
dokumentasi/API_FORM_A_H_ENTRY.md.

Assignment Plant-Jetty:

- GET    /plant-jetty-assignments
- POST   /plant-jetty-assignments (ADMIN)
- DELETE /plant-jetty-assignments/:id (ADMIN)

Dokumentasi payload dan filter lengkap: dokumentasi/API_SHIPMENT_VOYAGE.md.

Endpoint laporan legacy:

- GET    /reports
- POST   /reports
- GET    /reports/:id
- PATCH  /reports/:id
- DELETE /reports/:id
- POST   /reports/:id/depart
- POST   /reports/:id/arrive
- POST   /reports/:id/finish

Contoh membuat laporan:

{
  "reportNo": "RPT-2026-001",
  "vesselId": "UUID_VESSEL",
  "originTerminalId": "UUID_TERMINAL_ASAL",
  "destinationTerminalId": "UUID_TERMINAL_TUJUAN",
  "unloadingMasterId": "UUID_UNLOADING_MASTER",
  "cargo": "Crude Oil",
  "operationType": "LOADING",
  "reportDateTime": "2026-09-03T08:00:00.000Z",
  "loadingMasterSurveyorName": "Nama Surveyor",
  "portName": "Balikpapan",
  "remarks": "Catatan"
}

Status perjalanan dan transisi:

DRAFT -> BERLAYAR -> SANDAR -> FINISH

- LOADING_MASTER mengisi data dan seal ketika DRAFT.
- Depart hanya berhasil jika point snapshot AVAILABLE dan required sudah
  SEALED dengan nomor segel, atau ditandai NOT_APPLICABLE.
- Point opsional, section tidak tersedia, NOT_APPLICABLE, dan dokumentasi
  tidak memblokir depart/finalisasi.
- Setelah BERLAYAR, data pemasangan seal terkunci.
- UNLOADING_MASTER menerima kapal dan mengubah status menjadi SANDAR.
- Pemeriksaan seal hanya dapat dilakukan ketika SANDAR.
- Finish/finalize hanya berhasil jika seluruh seal aktif sudah diperiksa dan
  menyimpan finalSnapshot immutable.
- Setelah FINISH, perjalanan bersifat baca saja.
- SUPERVISOR dapat menjalankan proses loading dan unloading.

Endpoint /reports tetap tersedia untuk kompatibilitas aplikasi dan laporan lama.
Validasi dan lifecycle lengkap: dokumentasi/API_SHIPMENT_LIFECYCLE.md.

6.13 Lampiran gambar dan dokumen

- POST   /reports/:reportId/attachments
- POST   /records/:recordId/attachments
- POST   /verifications/:verificationId/attachments
- GET    /attachments/:id
- GET    /attachments/:id/file
- DELETE /attachments/:id

Upload menggunakan multipart/form-data:

- file        Wajib; tipe File
- type        Opsional; PHOTO, DOCUMENT, atau OTHER
- description Opsional; maksimal 2000 karakter
- sequence    Opsional; bilangan bulat >= 0

Format file yang diterima: JPEG, PNG, WebP, PDF.
Batas default: 10 MB. Sistem memvalidasi signature/magic bytes file.
Lampiran loading hanya dapat ditambahkan ketika DRAFT. Bukti pemeriksaan pada
verification ditambahkan oleh proses unloading ketika SANDAR.

Contoh upload:

curl -X POST http://localhost:5001/api/v1/reports/REPORT_ID/attachments \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  -F "file=@/path/foto.png" \
  -F "type=PHOTO" \
  -F "description=Foto bukti pemasangan seal" \
  -F "sequence=1"

Contoh download:

curl http://localhost:5001/api/v1/attachments/ATTACHMENT_ID/file \
  -H "Authorization: Bearer ACCESS_TOKEN" \
  --output lampiran.png

10. STEP 8 - DOKUMENTASI ATTACHMENT DAN TANDA TANGAN
======================================================================

Attachment mendukung JPEG, PNG, WebP, dan PDF dengan owner REPORT,
SECTION, SEALING_RECORD, atau VERIFICATION. Metadata meliputi caption,
sequence, section A-H, compartment/titik, nama file aman, MIME, ukuran,
dan checksum SHA-256. Preview menggunakan /attachments/:id/preview dan
download menggunakan /attachments/:id/download. Endpoint /file tetap
menjadi alias kompatibilitas untuk preview.

Signature mendukung CHIEF_OFFICER, TERMINAL_REPRESENTATIVE, dan SURVEYOR,
dengan maksimal satu row per role per laporan. Nama, waktu, user opsional,
serta file JPEG/PNG/WebP/PDF dapat disimpan. File signature mempunyai
endpoint /signatures/:id/file, /preview, dan /download.

Dokumentasi dan tanda tangan tetap opsional. Semua mutation ditolak setelah
laporan FINISH. Upload/delete/penggantian file memakai cleanup atau rollback
jika transaksi database gagal. Metadata attachment dan signature ikut masuk
ke finalSnapshot. Detail kontrak ada di API_DOCUMENTATION_SIGNATURE.md.

11. STEP 9 - GENERATOR XLSX RESMI
======================================================================

Generator memakai template Form Segel Baru sesuai TKO (edit1).xlsx dengan
checksum SHA-256 d9a6e738b7551357099f2443207a11396ed2397baf1aeafb1cd4d0c616dae963.
Template dibaca immutable dan generator menolak file yang checksum-nya berubah.

POST /reports|voyages|shipments/:reportId/xlsx membuat artefak dari finalSnapshot
laporan FINISH. GET .../xlsx/preview menampilkan inline dan GET .../xlsx/download
mengunduh file. Hasil menyertakan header shipment, A-H dinamis, nomor segel,
NOT_APPLICABLE, serta nama/gambar tanda tangan.

Overflow dibuat sebagai worksheet Segel Lanjutan N yang mengklon layout resmi.
Logo, merge, style, ukuran row/column, margin, orientasi, page break, calc chain,
dan printer settings dipertahankan. Template sumber tidak mempunyai defined
print area sehingga generator juga tidak mengarang print area baru.

Konfigurasi path: SEALING_XLSX_TEMPLATE_PATH dan XLSX_EXPORT_DIR. Detail kontrak,
mapping cell, continuation, authorization, serta error ada di API_XLSX_EXPORT.md.

======================================================================
12. STEP 10 - GENERATOR PDF DAN APPENDIX DOKUMENTASI
======================================================================

Generator memakai Form Segel Mengacu B3.1-612 TKO Pengelolaan Segel Rev. 0.pdf
sebagai background immutable tiga halaman A4. Checksum template adalah
231031f64a1264c24508552b99466963938cccad64687a7a5400ebd4bbab48e6.
Nilai akhir ditumpuk dari finalSnapshot menggunakan font PDF standar yang tidak
bergantung pada instalasi font host.

POST /reports|voyages|shipments/:reportId/pdf membuat dan menyimpan satu
PdfArtifact per report FINISH. GET .../pdf/preview dan .../pdf/download membaca
byte-stream yang sama setelah pemeriksaan ukuran dan checksum; generate berulang
tidak merender ulang. Overflow memakai salinan set tiga halaman resmi.

Foto opsional JPEG/PNG/WebP dari report, section, sealing record, atau verification
ditambahkan sesudah form sebagai appendix A4 3 x 3, dengan caption dan urutan.
Dokumen PDF tetap dapat diunduh melalui API attachment dan tidak diperlakukan
sebagai foto. Detail endpoint, metadata, authorization, dan error tersedia pada
API_PDF_EXPORT.md.
