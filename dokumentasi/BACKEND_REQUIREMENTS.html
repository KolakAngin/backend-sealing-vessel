P1

1. Unloading Master dapat membuat shipment

Status Backend: ✅ Selesai diimplementasikan.

Implementasi Backend:

  • POST /shipments dan POST /voyages kini mengizinkan role UNLOADING_MASTER (selain ADMIN, SUPERVISOR, dan LOADING_MASTER).
  • loadingMasterId opsional jika dibuat oleh Unloading Master (dapat dikosongkan atau dipilih dari /users/assignable?role=LOADING_MASTER).
  • Pembuat otomatis ditetapkan sebagai unloadingMasterId jika tidak diisi eksplisit, sehingga shipment langsung tampil di list miliknya (GET /shipments).
  • Endpoint GET /shipments/:id dapat diakses oleh Unloading Master pembuat.
  • Endpoint PATCH /shipments/:id, PATCH /voyages/:id, DELETE /shipments/:id, dan DELETE /voyages/:id mengizinkan Unloading Master pembuat mengedit dan menghapus shipment miliknya selama status masih DRAFT.
  • Unloading Master lain tidak berhak mengedit atau menghapus shipment tersebut (403).

Yang harus dilakukan Frontend:

  1. Buka tombol "Tambah Shipment": Izinkan user dengan role UNLOADING_MASTER untuk membuka form dan membuat shipment (POST /api/v1/shipments atau POST /api/v1/voyages).
  2. Form Buat Shipment:
    • Jadikan field pemilihan Loading Master (loadingMasterId) opsional, atau sediakan pilihan dari daftar assignable Loading Master.
    • Field Plant dan Jetty bongkar tetap tidak perlu ditampilkan / tidak wajib diisi pada saat pembuatan.
  3. Aksi Edit & Hapus:
    • Tampilkan tombol Edit dan Hapus pada detail / card shipment buatan Unloading Master selama berstatus DRAFT.
    • Gunakan PATCH /api/v1/shipments/:id untuk edit dan DELETE /api/v1/shipments/:id untuk hapus.

2. Tujuan bongkar ditetapkan Unloading Master saat kapal sandar

Status Backend: ✅ Selesai diimplementasikan.

Implementasi Backend:

  • Endpoint POST /api/v1/shipments/:id/arrive (dan /voyages/:id/arrive) kini menerima payload:
    {
  "occurredAt": "2026-10-17T03:00:00.000Z",
  "dischargePlantId": "uuid-plant",
  "dischargeJettyId": "uuid-jetty",
  "remarks": "opsional"
}
  • Validasi pasangan Plant–Jetty aktif dan terdaftar pada PlantJettyAssignment (mengembalikan 400 jika tidak cocok).
  • Dibuat audit log SHIPMENT_DESTINATION_ASSIGNMENT dengan userId Unloading Master yang menetapkan.
  • DESTINATION_ASSIGNMENT_REQUIRED dihapus dari validasi keberangkatan (depart). Kapal dapat berangkat ke status BERLAYAR tanpa tujuan bongkar.
  • Finalisasi BA LOADING (POST /shipments/:id/ba/loading/finalize) dan pencetakan PDF muat tidak lagi mewajibkan tujuan bongkar. PDF muat menampilkan label "belum ditetapkan" jika tujuan bongkar belum ditentukan.
  • Validasi finalisasi BA UNLOADING dan transisi FINISH mewajibkan tujuan bongkar (dischargePlantId dan dischargeJettyId) sudah ditetapkan (DESTINATION_REQUIRED).
  • Endpoint PUT /shipments/:id/destination-assignment oleh Loading Master tetap dipertahankan saat status DRAFT untuk backward compatibility jika tujuan sudah diketahui sejak awal muat.

Yang harus dilakukan Frontend:

  1. Dialog "Konfirmasi Kapal Sandar":
    • Pindahkan dropdown pemilihan Discharge Plant dan Discharge Jetty ke dalam dialog/modal konfirmasi saat Unloading Master menekan tombol "Kapal Sandar".
    • Muat pilihan Plant aktif dan Jetty aktif yang terdaftar untuk Plant tersebut (berdasarkan data master).
    • Kirim dischargePlantId dan dischargeJettyId di dalam body request POST /api/v1/shipments/:id/arrive.
  2. Hapus Blokir Keberangkatan pada Loading Master:
    • Hapus kewajiban / tombol wajib "Tetapkan Tujuan Bongkar" sebagai syarat klik "Kapal Berangkat" (depart). Loading Master dapat langsung memberangkatkan kapal setelah BA LOADING difinalisasi tanpa perlu menginput tujuan bongkar.
  3. Proteksi Finalisasi BA UNLOADING:
    • Pastikan sebelum Unloading Master menekan "Finalisasi BA UNLOADING", tujuan bongkar sudah terisi. Jika belum (misal sandar tanpa mengisi tujuan), tampilkan dialog untuk melengkapi tujuan bongkar.

3. CRUD titik segel per shipment oleh Loading Master

Arahan. Loading Master dapat menambah, mengubah, dan menghapus titik segel di dalam shipment. Perubahan hanya berlaku pada snapshot shipment tersebut dan tidak mengubah master kapal (VesselSealingPoint).

Kondisi sekarang. Belum ada endpoint. Snapshot form dibentuk sekali saat prepare-seals dan tidak bisa ditambah/dikurangi. SealingRecord.vesselSealingPointId dan Attachment.vesselSealingPointId wajib merujuk titik master, sehingga titik yang hanya ada di shipment tidak bisa punya record, segel, atau foto.

Yang diinginkan.

  1. Identitas titik per shipment (mis. tabel ShipmentSealingPoint) dengan vesselSealingPointId nullable: terisi untuk titik dari master, null untuk titik tambahan. SealingRecord dan Attachment merujuk ke identitas ini.

  2. Endpoint (Loading Master yang ditugaskan, Supervisor, Admin; hanya DRAFT dan sebelum BA LOADING final):

    Method Path Fungsi
    POST /shipments/:id/form/points Tambah titik: sectionCode, templateId, compartmentId?, side?, displayName, locationName?, required
    PATCH /shipments/:id/form/points/:pointId/definition Ubah nama, lokasi, required, urutan
    DELETE /shipments/:id/form/points/:pointId/definition Hapus titik dari snapshot (reason wajib)

    Path /definition dipakai agar tidak bentrok dengan PUT/PATCH/DELETE /form/points/:pointId untuk isian segel.

  3. Aturan yang perlu disepakati: soft-delete titik asal master (dengan alasan dan pelaku), titik bersegel harus dikosongkan dulu sebelum dihapus, validasi depart menghitung titik tambahan, audit log, penanda origin: "VESSEL" | "SHIPMENT".

Frontend sementara. Hanya isian segel, "Tandai N/A", dan "Kosongkan Titik".

4. Validasi format nomor segel

Kondisi sekarang. sealNumber hanya divalidasi 1–100 karakter, trim, uppercase, dan unik per shipment (transaction.schema.ts:121, :178-179). Nomor seperti 123, 0000, atau ---- diterima. W. 21114069 dan W.21114069 dianggap nomor berbeda.

Yang diinginkan. Tetapkan format resmi dari TKO/SOP/supplier segel (pola digit, panjang, prefix W.), tegakkan di formSealValue, createSealBody, dan updateSealBody, dan normalisasi variasi penulisan prefix:

→ 400 { "message": "Validasi request gagal",
        "details": [ { "path": ["body","seals",0,"sealNumber"],
                       "message": "Format nomor segel tidak sesuai (contoh: W.21114069)" } ] }

Frontend sementara. Tidak menambah aturan format sendiri agar tidak menolak segel asli. Hasil pindai wajib dikonfirmasi petugas.

5. Snapshot 0 titik tetap bisa berangkat; penjaga ganti kapal

Kondisi sekarang.

  • prepare-seals membuat snapshot walaupun kapal tidak punya titik aktif (pointCount: 0), dan validasi depart hanya memeriksa titik required. Shipment bisa berangkat tanpa satu pun segel.
  • Penjaga ganti kapal menghitung baris sealingRecord, bukan keberadaan snapshot (transaction.service.ts:298). Snapshot 0 titik tidak membuat record, jadi kapal masih bisa diganti, lalu form rusak permanen (FORM_SNAPSHOT_INVALID).

Yang diinginkan.

  1. prepare-seals menolak bila kapal tidak punya titik aktif (400 "Kapal belum memiliki titik segel aktif"), atau validasi depart melaporkan FORM_EMPTY.
  2. Penjaga ganti kapal memakai keberadaan snapshot:
    if (input.vesselId && input.vesselId !== old.vesselId && old.formConfigurationSnapshot !== null) {
  throw new AppError(400, "Vessel tidak dapat diubah setelah titik segel disiapkan");
}

Frontend sementara. Peringatan saat memilih kapal tanpa titik aktif; pilihan kapal dikunci setelah snapshot terbentuk.

6. Foto pemasangan terhubung ke segel

Kondisi sekarang. Foto pemasangan disimpan sebagai lampiran SECTION dengan vesselSealingPointId, tanpa relasi ke Seal (model Attachment hanya punya sealingRecordId, verificationId, vesselSealingPointId). Melepas segel, mengosongkan titik, atau menandai N/A tidak menyentuh fotonya, sehingga foto segel yang sudah dilepas tetap tercetak di BA.

Yang diinginkan.

POST /shipments/:id/sections/:code/attachments
multipart: file, type=PHOTO, vesselSealingPointId=…, sealId=…

Saat segel menjadi REPLACED/REMOVED atau titik dikosongkan, lampiran dengan sealId tersebut ikut diarsipkan dan tidak dicetak di BA.

Frontend sementara. Foto dicocokkan lewat caption (Foto pemasangan segel NOMOR – titik) dan dihapus bersama segelnya. Cara ini hanya andal untuk foto yang diunggah aplikasi ini.

P2

7. Lampiran lintas owner dalam satu request

Kondisi sekarang. Setiap endpoint daftar hanya mengembalikan satu owner (attachment.service.ts:295-296). Foto titik harus diambil per section (hingga 8 request per shipment), ditambah satu request per verifikasi.

Yang diinginkan. GET /shipments/:id/attachments?scope=all mengembalikan lampiran semua owner beserta ownerType, sectionCode, vesselSealingPointId, verificationId. Tanpa scope, perilaku lama tetap (hanya REPORT).

8. Nomor segel terbaca pada verifikasi

Kondisi sekarang. SealVerification hanya menyimpan condition, verifiedAt, remarks. Ketidaksesuaian nomor dicatat frontend sebagai teks di remarks, sehingga tidak bisa dicari atau dilaporkan.

Yang diinginkan. Kolom scannedSealNumber String? pada POST /seals/:id/verify, opsional dengan penanda turunan numberMatches yang dihitung server.

9. Aturan pemeriksaan ulang (verifikasi ganda)

Kondisi sekarang. verifySeal (transaction.service.ts:2300) menerima verifikasi berulang untuk segel yang sama sampai BA UNLOADING final; status segel mengikuti hasil terakhir. BA PDF memuat semua verifikasi beserta fotonya (ba-pdf-export.service.ts:308).

Yang diinginkan. Resmikan pemeriksaan ulang di dokumentasi dan cetak hanya verifikasi terbaru per segel (termasuk fotonya), atau sediakan endpoint koreksi resmi (PATCH /verifications/:id dengan audit). Bila tidak diizinkan, tolak dengan 409.

Frontend sementara. Tombol "Periksa Ulang" membuat verifikasi baru lalu menghapus foto verifikasi lama.

10. Detail field pada error unik 409

Kondisi sekarang. Pelanggaran unique Prisma (P2002) selalu menjadi pesan generik tanpa field (src/middleware/error-handler.ts:39-40), misalnya untuk nomor shipment duplikat.

Yang diinginkan. Petakan error.meta.target ke details:

{ "success": false, "message": "Data dengan nilai unik tersebut sudah tersedia",
  "details": [{ "path": ["body", "shipmentNumber"], "message": "Nomor shipment sudah digunakan" }] }

11. GET /ba/:phase sebelum dokumen ada, dan dokumen BA dari draft PDF

Kondisi sekarang.

  • GET /shipments/:id/ba/:phase membalas 404 sampai dokumen BA dibuat (tanda tangan pertama, draft PDF, atau finalisasi). Browser mencatat 404 ini sebagai error walaupun kondisinya normal.
  • Generate draft PDF BA juga membuat BeritaAcaraDocument. Setelah itu DELETE /shipments/:id ditolak 409 (transaction.service.ts:529), padahal belum ada tanda tangan atau data BA yang diisi.

Yang diinginkan.

  • GET /ba/:phase membalas 200 dengan dokumen virtual saat belum dibuat, mis. { "id": null, "phase": "LOADING", "status": "DRAFT", "signatures": [], "signatureValidation": { … } }.
  • Draft PDF tidak membuat dokumen BA, atau hapus shipment hanya ditolak bila BA sudah punya tanda tangan atau sudah final.

Frontend sementara. Membaca GET /ba/:phase/signatures dulu (selalu 200) dan hanya meminta dokumen bila sudah ada tanda tangan. Menu hapus disembunyikan bila BA Muat sudah punya tanda tangan; kasus draft PDF tetap menampilkan pesan 409 dari backend.

12. Hardening keamanan

Kondisi sekarang. Belum ada rate limit/lockout pada POST /auth/login, belum ada header keamanan (helmet), dan JWT berlaku 8 jam tanpa refresh token atau pencabutan.

Yang diinginkan.

  1. Rate limit login, mis. 10 percobaan per 15 menit per IP + username, response 429.
  2. helmet() untuk header keamanan standar.
  3. Access token lebih pendek (mis. 1 jam) plus endpoint refresh, atau daftar token yang dicabut.
  4. Jangan menerima token lewat query string untuk preview file; frontend sudah memakai header Authorization.

13. Penyimpanan file denah kapal di backend (opsional)

Kondisi sekarang. Denah hanya berupa URL teks (Vessel.drawingFileUrl / drawingLink), sehingga file harus disimpan di server lain yang biasanya dapat diakses tanpa login dan perlu CORS untuk Flutter Web.

Yang diinginkan (bila denah perlu dilindungi login atau diunggah dari panel admin).

PUT /api/v1/vessels/:id/drawing   (ADMIN, multipart "file": PNG/JPEG/WebP)
GET /api/v1/vessels/:id/drawing   (AUTH, stream file, Cache-Control private)

Setelah upload, drawingFileUrl diisi URL endpoint GET. Aplikasi tidak perlu diubah karena URL backend sudah dimuat dengan header Authorization.
